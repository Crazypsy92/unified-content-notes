## 情感观点分析：通用观点分析的领域专项

**模块类型：领域扩展；继承基础模块：** [通用观点分析](../core/argument-analysis.md)。

**模块职责：分析关系内容，不负责独立排版。** 通用模块决定一个话题一个标题、观点表格、完整浓缩正文、折叠原文与 Obsidian 风格；本模块只补充亲密关系的观察、推理和边界判断，**不复制基础排版规范，不再另造一套模板**。

## 什么时候适用

- **适用：** 用户要求分析恋爱观、吸引力、择偶、亲密关系、婚姻、冷处理、争吵、分手、伴侣付出与沟通的观点材料。先加载基础观点分析，再应用本模块。
- **按需适用：** 真实情侣聊天或个人情感经历，若用户明确要求关系层面的解读，可以与 [对话分析](../core/dialogue-analysis.md) 或 [叙事分析](../core/narrative-analysis.md) 配合；只有观点主导时才强制使用观点表格。
- **不自动适用：** 职场 / 社会评论里偶然出现一段恋爱案例，但核心论点不在关系领域；只按通用结构处理。
- **不适用：** 用户只要求“原文一个字不改，单纯排版”的任务，优先执行 [只改格式](../core/format-only.md)，不要额外关系诊断。
- 同一篇有观点 + 对话 + 个人感悟时，以实际主结构为主，保留来源层级，不重复生成若干版本。

## 关系领域新增的分析视角

仅对材料确实提供的内容展开，不强制全部覆盖：

1. **双方关系与阶段**：认识 / 暧昧 / 热恋 / 长期关系 / 分手等，已知事实才写。
2. **具体行为与对话**：谁做了什么、表达了什么、回应了什么；用真实互动而不是贴标签。
3. **期待与需求**：陪伴、回应、尊重、空间、边界、承诺是否明确表达；没有表达时不能当成已知诉求。
4. **互动模式与责任**：是一次事件还是长期重复？一方的行为可能如何影响另一方？能否区分各自责任，而非单方归因。
5. **情绪与解释**：可观察情绪、当事人自述与对其动机的假设分开；不能把推测写成事实。
6. **关系的可持续性**：双方是否愿意协商、兑现约定、分担付出、尊重选择；长期结果未知时不要替人判定关系结局。

## 核心案例分析：保持两条轨道

- **事实轨**：事件背景、双方行为、原话、回应、结果。必须被完整保留到通用“浓缩正文”，不因做情感分析而缩成“双方存在沟通问题”。
- **解释轨**：在事实后说明某个行为可能被如何理解，哪些证据支持、哪些没有；允许给出不同解释和可讨论的边界。
- 例：一方临时加班取消约会，已经解释并协商改期；另一方失望。可以分析“失约造成失望”和“解释、补约体现回应”，但不能直接推断“对方不爱了”或“一方过于依赖”。
- 对话中双方说法矛盾时分别保留，不能替一方补造动机；用户个人评价与讲者观点分开。

## 判断边界

- 不凭一次未回消息、争吵或一个人提供的片段就诊断人格、依恋类型、精神问题，或判定“冷暴力 / PUA / 操控 / 情绪虐待”。强标签需要具体行为证据。
- 区分正常陪伴需求、过度索取、长期忽视、主动沟通与控制。独立不等于不需要陪伴，理解对方不等于无条件迁就。
- 对“所有男人 / 女人都这样”的泛化、性别刻板印象、未经核验的生理周期与心理学断言，只标注可支持范围，不以反向刻板印象代替判断。
- 情感中的主体性不等于以自己的感受作为关系的唯一标准；考虑双方权利、需求和付出。
- 原文有用户反思时忠实保留，不将用户观点与创作者观点合并。
- 关系分析应有温度但不额外煽情；事实充分时分析深入，材料不足时保持克制。

## 成稿形式

**完全沿用通用观点分析型输出：** 一个原始话题标题 → 来源统一标注 → 观点速览表格 → 含完整案例和逻辑的浓缩正文 → 按需个人感悟 / 观点辨析 → 可折叠原文。情感模块改变分析内容的深度，不改变页面结构。

## 技术基础与面试知识点整理

**适用范围：** 嵌入式基础、RTOS、MCU、Cortex-M、外设驱动、通信协议、存储器、传感器、控制算法、功能安全，以及其他以“面试题 / 知识点”为基本单元的技术笔记。

**本模块的目标：** 把知识点整理成容易复习、容易口头表达、能联系工程实践的笔记。重点是解释清楚，而不是把每个知识点拆成许多小标题或装饰性卡片。

## 一、先确定材料边界

- 保留用户给出的原始题目和关键术语，不擅自改成另一个问题。
- 以用户提供的资料为主要依据。用户只要求排版时，不额外纠错、扩写或替换原有技术口径。
- 用户要求补充、核验或扩展时，区分“原始材料内容”“补充解释”“外部核验结果”；对不确定的参数、芯片差异和 API 行为明确标注。
- 通用原理、具体 RTOS / MCU 实现、厂商特定 API 必须分开，不把 FreeRTOS 的实现规则说成所有 RTOS 的共同规则。
- 工程案例要说明是用户真实经历、官方文档示例、可复现实验模型还是方案推演；不得把推演说成已实测。

## 二、知识点的唯一标题规则

技术面试笔记默认使用以下层级：

```markdown
# 文档标题

## 一、章节名称

### 1. 原始面试题目？

题目正文……

### 2. 下一个面试题目？

题目正文……
```

**硬性要求：每道题只保留一个题目标题。**

- 文档标题使用 `#`，章节使用 `##`，题目使用 `###`。
- 题目内部禁止使用 `####` 或更低级标题。
- 不把“核心回答、工作原理、优缺点、应用场景、面试追问”等写成 Markdown 小标题。
- 这些内容确有必要时，用普通段落开头的加粗短语组织，例如：`**核心回答：**`、`**工作原理：**`。
- 不强制每道题都具备同一组标签；内容简单就简短回答，复杂内容再补充原理、对比和工程案例。
- 目录只列章节与题目，不把题目内部的粗体标签放进目录。

## 三、正文组织原则

优先采用自然、连续的解释结构：

1. **核心回答：** 先用一段话说明是什么、解决什么问题。
2. **原理与关键机制：** 按因果顺序解释，不必再拆成多个标题。
3. **关键区别：** 确实存在比较对象时使用 Markdown 表格；没有比较需求时不强行造表。
4. **工程应用：** 用简洁案例说明在 MCU / RTOS / 驱动 / 工业控制中的用途。
5. **易错点与限制：** 只保留真正容易混淆或会影响工程正确性的内容。

可使用以下形式，但不要把它们变成子标题：

- `**核心回答：**` 一段话解释结论。
- `**工作原理：**` 后接连续说明或列表。
- `**工程例子：**` 说明真实或明确标注来源的案例。
- `**注意：**` 指出边界、风险或芯片差异。

**不要为了看起来“内容丰富”而机械增加一、二、三、四等小标题。** 如果一个知识点本身只有两层逻辑，用段落和列表就足够。

## 四、Obsidian 视觉与 Callout 使用

- 普通 Markdown 正文是默认样式：段落、列表、表格、引用和适量加粗。
- 不要每道题都放一个 `[!abstract]` 核心回答色块。
- Callout 只用于真正需要从正文中凸显的内容，例如跨章节的关键结论、安全风险或必须记住的限制。
- 建议全篇 Callout 不超过题目数的 20%；通常每个章节最多 1 个。若没有特别重要的提醒，可以完全不使用 Callout。
- 不连续堆叠 Callout，不把普通解释、每个例子和每张表都装进背景色块。
- 不使用 CSS snippets、HTML、内联 style 或自定义文字颜色；依靠 Obsidian 主题原生 Callout 背景、加粗和留白形成层次。
- 章节之间可以使用少量 `---`；题目之间通常不需要分割线。
- 段落建议围绕一个完整意思展开，避免整页成为一堵文字墙；也不要把每句话机械拆成单独段落。

## 五、Obsidian MathJax 公式规则

Obsidian 使用 MathJax 渲染数学表达式。面向 Obsidian 的笔记统一采用美元符号分隔，避免混用多种 LaTeX 文档环境的定界符。

**行内公式：** 使用单个美元符号包围，例如：

```markdown
采样周期为 $T_s=1/f_s$，其中 $f_s$ 为采样频率。
```

**块级公式：** 使用独立成行的双美元符号，前后留空行：

```markdown
$$
u(t)=K_p e(t)+K_i\int_0^t e(\tau)\,\mathrm{d}\tau
+K_d\frac{\mathrm{d}e(t)}{\mathrm{d}t}
$$
```

具体要求：

- 行内只用 `$...$`；块级只用单独成行的 `$$...$$`。
- 面向 Obsidian 的交付默认不使用 `\\(...\\)` 和 `\\[...\\]` 作为公式定界符。
- 公式不要放进三反引号代码围栏；代码围栏只用于展示源码。
- 保留 LaTeX 命令中的反斜杠，例如 `\frac`、`\int`、`\mathrm`、`\text`；不要把反斜杠额外转义成双反斜杠。
- 块级公式的开闭 `$$` 必须各自独占一行，前后留空行。
- 简单表达式优先使用行内公式；只有较长、需要独立阅读的公式才使用块级公式。
- 公式后解释变量、单位、适用条件和假设，不能只放一个公式而不解释含义。

## 六、Obsidian 导航

- 快速索引只列章节和题目。
- 使用 Obsidian 原生标题链接，例如 `[[#1. BOR 是什么？作用是什么？|BOR 与 PVD]]`。
- 不为题目内部的粗体标签创建链接。
- 检查链接文字与实际标题完全对应，避免标题调整后留下失效跳转。

## 七、交付前检查

- [ ] 文档标题、章节标题和题目标题层级正确。
- [ ] 每道题只有一个 `###` 题目标题，没有 `####` 内部标题。
- [ ] 目录只列章节和题目，没有重复目录或内部小标题。
- [ ] 正文以普通段落、加粗短语、列表和表格为主。
- [ ] 没有按题目机械套用 Callout；Callout 数量不超过题目数的 20%，且每个色块有明确价值。
- [ ] 没有 CSS、HTML、内联颜色或背景样式。
- [ ] 行内公式使用 `$...$`，块级公式使用 `$$...$$`，开闭配对且未放进代码围栏。
- [ ] 表格列数一致，内容确有比较价值。
- [ ] 技术参数、标准等级、芯片特性和 API 语义没有未经标注的猜测。
- [ ] 案例来源与验证程度清楚，不把方案推演说成实测。
